How to read this document

The document serves two purposes that can be followed independently. The analysis track (C2–C5) describes what the console actually does on the network: what starts at boot, which functions carry every packet, which structures and keys take part in sign-in. The engineering track (C6–C8) turns those findings into design decisions: where to intercept traffic, how to build a DashLaunch plugin, and what a community server must expose for the console to accept it as its own.

This document was written assuming the reader (human or language model) will implement the plugin and the servers on its basis — that is why C6–C8 end with concrete recommendations and pseudocode, and Appendix A carries complete export-ordinal tables needed for runtime function resolution.

Conventions

NetDll_connect(12) — module export name with its ordinal in parentheses, the key used for GetProcAddress resolution. 0x5801 — a hexadecimal constant value. References such as [S7] point to the source registry in Appendix C — every numeric fact in this document is tied to a community source or is explicitly marked otherwise.

The UNVERIFIED marker

Facts that could not be confirmed in at least one reachable community source are marked UNVERIFIED, together with a suggested way to verify them (usually: packet capture on an RGH console or analysis of xam.xex). No such fact should be treated as a design premise without independent verification.

Source policy

All knowledge comes exclusively from homebrew-community material: xboxdevwiki / Free60 / Xenon Library, GitHub repositories (xenia, exjam/xbox360-emu, hiddriver360/xkelib, insigniaDNS, ExCrypt), the Insignia and Team XLink services, conference talks (36C3, DEF CON 30) and forum archives. Vendor documentation (Microsoft Learn, Xbox Support) was deliberately excluded from the research process, per the task specification.

Chapter 1 · Intro
Purpose, scope and audience

1.1Purpose of this document

This document fully describes the network behavior of the Xbox 360 console as it connects to Xbox Live — from system start-up, through network-stack initialization, DNS name resolution and authentication, up to service traffic (title updates, marketplace, presence). This knowledge is the foundation for two engineering deliverables: (1) a DashLaunch plugin that redirects packets addressed to Xbox Live servers toward community servers, and (2) community servers capable of speaking the console's protocols and meeting its expectations well enough that an "online" session completes successfully instead of failing sign-in.

The document was commissioned for a top-tier technical audience — reverse-engineering engineers and large language models that will use it to write the plugin and server code. For that reason the priorities are factual precision (export ordinals, structure sizes, protocol constants) tied to mechanism explanations — no filler and no fabricated data. Wherever the community has not yet documented something, a "RE gap" section appears describing how to extract the missing fact, instead of a guess.

1.2Audience and how to use it

The document is designed to serve as a single source of truth for the implementer. Recommended working order:

  1. C2–C3 — understand which modules and functions carry the traffic (this defines the interception-point list).
  2. C4–C5 — understand the sign-in sequence and cryptography (this defines what the server must answer, and what cannot be "tricked" by DNS alone).
  3. C6 — choose the redirect layer (decision matrix with a hybrid recommendation).
  4. C7 — implement the DashLaunch plugin (complete skeleton + hook pseudocode).
  5. C8 — implement the server (components and their responsibilities).
  6. AX — ordinal tables for runtime function resolution.

1.3Scope and exclusions

In scope: the Xbox 360 console (all revisions, with emphasis on unlocked units — RGH/JTAG — on which a DashLaunch plugin can be loaded), the XNet/NetDll system network stack, the Xbox Live authentication variant used by this system, the XeCrypt/KeyVault cryptographic machinery, redirect infrastructure, and community-server design patterns.

Deliberately out of scope: the mechanics of the RGH/JTAG exploits themselves (we assume an already-unlocked console), Xbox One/Series-era protocols (mentioned only as evolution context — e.g. XSTS tokens), license circumvention (this document covers network behavior, not piracy), and Microsoft's production servers — the document describes only what the console does and what can be built independently from community research.

Business context (2026)

The Xbox 360 store and marketplace were retired in 2024 and companion services are being wound down — exactly the scenario that played out earlier on the original Xbox, where the community (the Insignia project) successfully resurrected Xbox Live 1.0 after its April 15, 2010 shutdown.[S10][S12] This document is a roadmap for the same operation on the Xbox 360 platform.

1.4Source policy

The research rule adopted: community sources only. The source registry (Appendix C) includes engineering wikis (xboxdevwiki, Free60, Xenon Library), community emulator and tool source code (xenia, exjam/xbox360-emu, hiddriver360/xkelib, ExCrypt, insigniaDNS), community-service documentation (Insignia, Team XLink), conference talks (36C3 2019, DEF CON 30) and press/encyclopedic articles. No technical fact was taken from Microsoft Learn or Xbox Support; such pages were skipped whenever they appeared in search results. Numeric data (ordinals, structure sizes, constants) was cross-verified in at least two independent repositories where possible (see the companion Work Report — methodology).

Chapter 2 · Foundations
Xbox 360 software architecture

Before networking, we must establish where the network functions live in the system — because they define the plugin's interception points. The Xbox 360 is a hypervisor-based console: sensitive operations (cryptography, keys, image loading) run in the hypervisor (HV), while the OS and applications run above it. Everything starts from a chain of bootloaders, each RSA-verifying the next.[S2][S3]

2.1Boot chain

Start-up sequence (retail, simplified): 1BL (CPU ROM) loads and verifies CB; CB prepares keys and loads CD, which decrypts and starts HV + kernel (kernel.bin). After kernel init, the xam.xex module (Xbox Application Model — the system application layer) starts and, among other things, brings up the network; the dashboard (dash.xex) loads last.[S2][S3] For traffic redirection two moments matter: XNet initialization inside xam (the system network stack) and title loading — titles import their network functions from xam.

2.2Hypervisor and sc syscalls

The HV exposes 117 procedures invoked with the sc instruction (call number in register r0, arguments in r3–r9).[S4][S18] Relevant to network-identity operations are the families: HvxKeys* (KeyVault access: HvxKeysGetKey(55), HvxKeysSaveKeyVault(53), HvxKeysRsaPrvCrypt(57), HvxKeysHmacSha(58), HvxKeysAesCbc(59), HvxKeysDes2Cbc(60)), HvxSecurity* (81–89) and HvxKeysGenerateRandomKey(49). The kernel — and XAM through it — uses these for all identity-related cryptography. A plugin does not call HV syscalls directly; it uses kernel/XAM exports. But this layer explains why console identity cannot be forged without the KeyVault secrets.

2.4Consequence for redirection

All network traffic of titles and the dashboard passes through the NetDll_* exports of xam.xex (Chapter 3). This is the fundamental good news for the plugin author: neither the kernel nor the hypervisor needs patching — hooking export-table entries in xam, the module titles link against, is sufficient. The bad news: the sign-in/cryptography layer (C5) uses console secrets from the KeyVault, so a community server must accept console identity by other means than copying Microsoft keys — exactly what Insignia did for the original Xbox (C9).

Chapter 3 · Networking
The XNet network stack

The Xbox 360 does not expose "plain" system sockets to programs. Titles and the dashboard use the NetDll_* export family of xam.xex, which wraps: (a) a Winsock2-style socket API (TCP/UDP), (b) the XNet layer — a secure, address-virtualizing superset of sockets, and (c) the auxiliary Xnp layer (XNet platform) holding configuration, the machine account and connection security state.[S4][S5][S6] All outgoing application traffic flows through these exports — which is why the plugin's interception list (C6/C7) is in practice a short list of NetDll functions.

3.1Socket API — NetDll ("X360 Winsock")

The socket function set is nearly 1:1 with Winsock2, except every function takes a leading XNCALLER_TYPE parameter identifying the calling context: XNCALLER_TITLE(1) for games, XNCALLER_SYSAPP(2) for system apps, XNCALLER_XBDM(3), XNCALLER_TEST(4).[S5][S6] The stack checks the caller type — a system app gets different privileges than a title. A redirect plugin must remember this: dashboard and game calls go through the same exports, but in different contexts.

3.2XNet — secure addressing and session keys

The XNet layer introduces the "secure address" abstraction. A game never handles a peer's raw IP: it receives the peer's XNADDR structure (online addresses plus a 20-byte identifier abEnet/abOnline) along with an XNKID (session id) and XNKEY (session key), then calls NetDll_XNetXnAddrToInAddr(57), which returns a secure IN_ADDR — a handle used in subsequent socket calls.[S5][S6] (XNKID, XNKEY) pairs are registered via NetDll_XNetCreateKey(54) / NetDll_XNetRegisterKey(55). Traffic on sockets bound to such an address is encrypted and authenticated by XNet — this is the Xbox "secure network", known from the original console.[S10]

XNADDR structure (big-endian layout, 38 B)

ina (4 B) — local IP (0 if not static); inaOnline (4 B) — online IP (0 if offline); wPortOnline (2 B) — online port; abEnet[6] — NIC MAC address; abOnline[20] — console online identifier.[S5] Tools and libraries (e.g. the 360 port of RakNet) read abEnet to generate identifiers — zeroing these fields crashes games, as xenia researchers' comments confirm.[S5]

3.3Configuration, DNS and options

The console's network configuration (static/DHCP/PPPoE, DNS servers, gateway, UPnP data) lives in the XNetConfigParams structure of 492 bytes (0x14 B hash, 8 B confounder, then: machine name, flags, MAC/IP/mask/gateway, two DNS servers, DHCP host, PPPoE user/pass/server, lease fields, UPnP MAC and port).[S6] These parameters are persisted in flash and handled by the NetDll_XnpLoadConfigParams(101)/SaveConfigParams(102)/Config(104) family — the DNS settings configured in the dashboard are exactly this structure.

Name resolution is asynchronous via NetDll_XNetDnsLookup(67): you pass a hostname and an event (WSAEVENT); on completion an XNDNS structure is filled (status, address count cina, array of up to 8 addresses aina[8]) and later freed with NetDll_XNetDnsRelease(68).[S5][S6] This is the second key interception point — a DnsLookup hook can return our own addresses for service names before anything reaches a real DNS server.

The XNet layer also exposes options read/written via NetDll_XNetGetOpt(78)/SetOpt(79). Security-relevant option ids include: XNKID_SECURITY 0x138C, SOCK_SECURITY 0x138D, PRIMARY_SG_NONCE 0x1398 (the Secure Gateway nonce!), and SEC_ASSOC_INFO 0x1399 (a dump of the XnSecAssocInfo structure, 0x78 B — the current security association with XNKID@0x10, XNADDR@0x18, service id, and NAT address/port).[S6] These options show that session security state is fully introspectable from XAM — a plugin can read it and understand whom the console "thinks" it is talking to.

Security socket options — what they mean for a community server

SO_MARKINSECURE 0x5801 and SO_GRANTINSECURE 0x5803 allow a socket to be marked as not using XNet protections (bool TRUE).[S6] In community practice this means an "insecure" session can be built and the cryptographic PA-DATA skipped where we choose — but beware: titles may check connection status and refuse to work. A community server should implement the full secure path first, and treat insecure mode as a fallback for purely system-level traffic (e.g. title-list downloads).

3.4VDP sockets and game traffic

The SOCK_VDP protocol (Voice/Data Protocol) is the UDP variant with an XNet overlay in which voice and game data flow over prioritized channels. In NetDll_WSASendTo(25) on a VDP socket, buffer zero carries the game-data length and buffer one carries the (still unencrypted) game data; the XNet layer then prepends its security header and encrypts the payload with the XNKEY session key.[S5] Practical consequence: gameplay traffic cannot be understood or rewritten without the session keys, but a community server can either relay the encrypted packets (relay mode) or issue its own XNKID/XNKEY pairs ("new session" mode) — see C8.

3.5QoS — link-quality probing

Before an online session the console measures path quality: NetDll_XNetQosListen(69) enables probe listening, NetDll_XNetQosLookup(70) probes an address list (probe/receive counters, min/median RTT in ms, up/down bandwidth in bit/s — the XNQOSINFO fields), and NetDll_XNetQosServiceLookup(71) measures quality toward the Live services.[S5][S6] A community server should answer QoS probes, otherwise the dashboard will report insufficient link quality and refuse the session — cheap to implement (a UDP responder) and critical for UX.

3.6System Link — heritage and the 30 ms limit

System Link (LAN play) uses UDP on port 3074 (IANA-registered for Xbox) and broadcasts on the special XNet address 0.0.0.1; sessions are identified by XNKID.[S1] All tunneling services build on this same mechanism (XLink Kai, LiNK — C9). Key engineering fact: the Xbox 360 drops a System Link connection when ping exceeds 30 ms — an anti-tunneling safeguard documented by Team XLink.[S12] An RGH console can patch the limit, but any community tunnel must account for it (regional arenas, relay placement).

3.7Interception-point summary

  • Service TCP traffic: NetDll_socket(3) → NetDll_connect(12) → send/recv — hooking 3 functions covers it all.
  • UDP/VDP traffic: NetDll_sendto(24)/WSASendTo(25) + recvfrom(20)/WSARecvFrom(21) — hook 4 functions.
  • DNS: NetDll_XNetDnsLookup(67)/Release(68) — hooking 2 functions replaces the name infrastructure.
  • Service HTTPS: NetDll_XHttp*(201–222) — if the community server speaks HTTPS, a certificate path is additionally required (C5.5, C6-L3).
  • Introspection: NetDll_XNetGetOpt(78) with SEC_ASSOC_INFO 0x1399 — live diagnostics of the security session.
Chapter 4 · Networking
Xbox Live connection sequence

This chapter reconstructs the chronology of states the console passes through from boot to a fully active online session, naming the functions observable in each state. The phase layout assumes a console with the final dashboard 2.0.17559 — older versions differ in UI details but not in the layer architecture described in C3.

4.1P0–P2: initialization and addressing

At startup XAM calls NetDll_XNetStartup(51) with startup parameters (XNetStartupParams: dgram/stream socket limits, buffer sizes, registered-key limits cfgKeyRegMax/cfgSecRegMax, QoS limits).[S5][S6] The dashboard then runs its test sequence: Ethernet link status via NetDll_XNetGetEthernetLinkStatus(75) (flags: active 0x01, 100/10 Mbps 0x02/0x04, full/half duplex 0x08/0x10), address acquisition via DHCP (or static/PPPoE from XNetConfigParams), and configuration completeness via NetDll_XNetGetTitleXnAddr(73), whose return flags describe the state: XNET_GET_XNADDR_PENDING (0), _ETHERNET (0x2), _STATIC (0x4), _DHCP (0x8), _PPPOE (0x10), _GATEWAY (0x20), _DNS (0x40), _ONLINE (0x80), _TROUBLE (0x8000).[S5] This is exactly the status ladder shown by the dashboard network test — every red icon in the UI corresponds to a specific flag.

4.2P3: DNS — how the console resolves names

The console uses the DNS servers from its configuration (via DHCP or set manually) and resolves names exclusively through the asynchronous NetDll_XNetDnsLookup(67).[S6] There is no system hosts file and no cache outside XNet — every query goes through this function. The current Live DNS server name is additionally available inside XAM via XNetLogonGetDnsString(313), confirming that the service keeps its own name record for the sign-in infrastructure.[S4] Practical conclusion: DNS redirection (layer L1, C6) is a complete mechanism — the console has no built-in override list and no IP pinning beyond DNS.

4.3P4: sign-in — challenge and tickets

The sign-in procedure itself is hidden inside xam: applications see it as asynchronous tasks started by NetDll_XNetLogonTaskStart(303) and pumped by NetDll_XNetLogonTaskContinue(305) (the XNetLogon* family also exposes a full state API: GetState(322), GetServiceInfo(306), GetUserPrivileges(307), GetExtendedStatus(315)).[S4] Below, in the Xnp layer, the challenge/response mechanics are visible: NetDll_XnpLogonGetChallenge(126) fetches a challenge, NetDll_XnpLogonSetChallengeResponse(128) submits the response.[S6] The presence of these exports alongside XnpGetSecAssocList(129) and XnpGetKeyList(130) reveals the architecture from C5: sign-in exchanges secrets with the server, and the outcome is a set of security associations and session keys available for introspection.

4.5Ports and transport

  • UDP/TCP 3074 — the IANA-registered Xbox port; System Link and Xbox 360 secure-socket traffic.[S1]
  • UDP 88 (Kerberos) and TCP 443 for HTTPS — repeated in community firewall threads; UNVERIFIED for the 360 in the available source material (confirm by capture).

4.6System time — a hard prerequisite

The console does not query public NTP in any way documented for the 360 (the time.xboxlive.com names belong to the XONE era — UNVERIFIED for 360).[S20] Instead, service time follows KDC time: the kernel exports XexSetLastKdcTime(735 / 0x2DF), storing the timestamp received from the authenticating server.[S5][S18] Engineering consequences: (a) session tickets have validity windows, so a wrong console clock means rejected tickets; (b) XHttp TLS certificate validation also depends on the clock; (c) the console RTC is bounded (the community-known "2025 cap" problem and the TimeFixer tool)[S22] — a community server must accept timestamps with wide tolerance and/or provide its own KDC time in the sign-in response.

Chapter 5 · Security
Authentication and cryptography

The authentication layer is where a "homemade Xbox Live" project wins or dies. Below we assemble the full picture from community material: machine identity (console certificate + machine account), user identity (profile with online key), the Kerberos-family ticket protocol with Xbox extensions (PA-DATA), and the Secure Gateway. Where 360-era attestation is missing, we lean on original-Xbox (Live 1.0) documentation — the same protocol lineage, as the 36C3/DEF CON speakers state outright.[S10][S11]

5.1Machine identity — certificate and account

Every console carries a manufacturer-signed RSA-2048 security certificate of 552 bytes (0x228), described in Free60 documentation and in the XE_CONSOLE_CERTIFICATE structure of the xkelib headers.[S15][S6] XAM hands it to the network stack via XNetLogonSetConsoleCertificate(308), and a title identifies itself separately via XNetLogonSetTitleID(314)/GetTitleVersion(311).[S4][S6] The certificate binds the console's public key to its identifiers — the console can prove its identity by signature (RSA operations run on the HV side through HvxKeysRsaPrvCrypt).

The second element is the machine account, attested for the original Xbox: created on first network test by the MACS.XBOXLIVE.COM server, based on a pre-shared key derived from the online key, the HDD key and a fixed key present in all Live binaries. The machine account alone only grants access to the user-account creation service (UACS); full services require a user account.[S10] The pattern transfers directly to a community server: console registration (verifying possession of console keys) + player registration (gamertag) — exactly how Insignia onboarding works (C9).

5.2The ticket protocol — Kerberos, Xbox edition

The xboxdevwiki documentation for Live 1.0 confirms: authentication uses the Kerberos protocol with proprietary Xbox customizations, and service access (matchmaking, statistics/leaderboards, dedicated game servers) goes through a Secure Gateway.[S10] Traces of this model are visible on the 360: the PRIMARY_SG_NONCE 0x1398 option is the SG gateway nonce, and the XexSetLastKdcTime export attests the KDC (Kerberos Domain Controller) time concept.[S5][S6] Xbox extensions in the pre-auth data (PA-DATA) cover types 131, 204 and 206 (Xbox version, title, title version) — these let the server bind a ticket to a specific game.[S10]

Three conclusions for the server implementer. First, the cryptography does not need to be broken — it suffices to be the server side of the exchange: the console sends a KR-format request, the server answers with its own tickets signed by its own service key. Second, the clock must agree (C4.6). Third, the exact ticket layout and field offsets for the 360 are an RE gap — to be extracted from xam.xex (analysis of the XnpLogon* call sites) or from dev-console captures.

5.3User identity — profile and online key

The player profile stores, among other things, the gamertag, the PUID (Passport User ID) and the online key; the Account file is encrypted with an "HMAC-RC4" scheme: HMAC-SHA1 with a KeyVault key (index 0x19; the retail key is known to the community) derives an RC4 key, which encrypts a confounder + 380-byte payload.[S14] Attested XAM exports for Live credentials are XamProfileSaveWindowsLiveCredentials(572)/LoadWindowsLiveCredentials(573).[S4] Conclusion: a community server can issue its own "gamertag + key" in the same profile-file format (Insignia's practice confirms this: web account registration + writing it to the console).

5.4System cryptography — XeCrypt and KeyVault

The kernel exports the full primitive set (Appendix A, Table A.6): RC4 (XeCryptRc4Key 395 / Rc4Ecb 396 / Rc4 397), AES-ECB/CBC/CBC-MAC/CTR, DES/3DES, MD5, SHA-1/256/384/512, HMAC-MD5/SHA, RSA (keygen, private/public encryption) and Diffie-Hellman (the BnDwLeDh* family — session-key exchange!).[S4][S5][S16] Console secrets live in the KeyVault (flash, HV-gated access); key operations run through the HvxKeys* family (C2.2). A universal reimplementation for offline analysis is the ExCrypt project.[S16]

5.5TLS and XHttp — the certificate problem

The console calls HTTP(S) services through the NetDll_XHttp* API (201–222) — a WinHTTP analog: XHttpOpen(203), XHttpConnect(205), XHttpOpenRequest(207), XHttpSendRequest(209), XHttpReceiveResponse(210), XHttpSetOption(215) etc.[S4][S5] The key question: where does the console keep its trusted TLS root CAs, and is validation bypassable? The community answer is currently incomplete: the location of the trusted-certificate store in the 360 system image remains UNVERIFIED (RE gap). It is known, however, that homebrew builds its own TLS 1.2 clients without external stores (example: the XboxTLS implementation in the X-Store project)[S19] — meaning an SSL stack is reachable from user-mode code. Practical bypass strategies on an RGH console are discussed in C6 (L3).

What cannot be done "the short way"

Without possessing manufacturer keys you cannot: forge a console certificate, sign a custom dashboard for an unmodified console, or stand up a TLS server the console will accept without touching its trust store or patching validation. Every real redirect project (Insignia included) solves this either on the console side (modification/RGH) or by designing services so they avoid TLS validated against the system store. This is not a limitation of this document — it is the boundary of cryptography.

Chapter 6 · Redirect
Redirect analysis — three layers

We now have the full picture of console behavior. Time to answer the main question: how do we make packets addressed to Xbox Live arrive at community servers? There are three complementary layers — L1: DNS, L2: export hooks inside the console, L3: TLS/certificate handling. This document recommends the hybrid L1+L2 approach, with L3 optional depending on the TLS decision. Each layer is discussed below and compared in a decision matrix at the end.

6.1L1 — DNS redirection

Mechanics: the console resolves all names via XNetDnsLookup (C4.2) using the configured DNS servers. By setting the community DNS server as primary (manually in the dashboard, via a DHCP option, or via a local forwarder like insigniaDNS on a LAN PC), we take over the entire *.xboxlive.com namespace and related names. This approach is operationally proven: Insignia instructs users to set primary DNS to 46.101.64.175 (secondary: public 8.8.8.8/1.1.1.1), and provides a local DNS server for restrictive ISPs.[S8][S9]

Pros: zero console modification (works even on retail units — how Insignia serves unmodified OG Xboxes), operational simplicity, full traffic coverage. Cons: depends on DNS/ISP settings; does not solve TLS (the hostname remains original, so the server certificate must pass console validation); traffic outside the name system (hard-coded IPs, if any exist — UNVERIFIED) is not captured. Recommendation: L1 as the base layer for every installation.

6.2L2 — export hooks inside the console (plugin)

Mechanics: a DashLaunch plugin (C7) patches entries in the xam.xex export table so that selected NetDll functions route through plugin code first. Hooks cover three traffic classes: (a) TCP — NetDll_connect(12): rewrite the sockaddr_in before the original implementation sees it; (b) UDP/VDP — NetDll_sendto(24)/WSASendTo(25) analogously; (c) names — NetDll_XNetDnsLookup(67): instead of waiting for DNS, synchronously return our own XNDNS structure. Pros: independent of DNS/ISP; precision (only chosen traffic is redirected — e.g. LAN stays untouched); on-console traffic logging/debugging. Cons: requires RGH/JTAG; patching risk (mitigated by the conventions in C7.4); dashboard updates could shift code offsets (we hook the table pointer, so we survive code relocation as long as the ordinal stays — and NetDll ordinals are stable because titles link by them).

6.3L3 — the TLS layer

If the community server exposes services the console calls via XHttp over HTTPS, the certificate-trust problem appears. Three paths: (a) avoid — design services over plain HTTP where possible (360 system traffic historically used HTTP for content CDNs — Table 4.1 shows the http:// patterns); (b) own trust — if the console root-CA store is modifiable (RE gap: location UNVERIFIED), import the community CA; (c) validation patch — the plugin patches the validation function on the XHttp path (location: to be determined by xam.xex analysis; community projects use this pattern for other purposes — e.g. the system-notification patch at 0x816A3158 demonstrates the "locate-path-patch" approach)[S7]. The L3 decision belongs to the server architect; this document recommends minimizing HTTPS (path a), because every touch of validation widens the failure surface.

This document's recommendation

Hybrid architecture: a community DNS server (L1) as the path for every console, a DashLaunch plugin (L2) as an enhancement for RGH/JTAG consoles (precise mapping, logging, fallback when DNS fails), and server services designed with minimal HTTPS (path L3-a). Chapter 7 · Redirect
DashLaunch plugin in practice

This chapter is a ready implementation base: project structure, the DashLaunch plugin API, and complete redirect-hook pseudocode. All facts come from the community guide (ClementDreptin/ModdingResources) and the code of existing plugins.[S7]

7.1Plugin loading model

DashLaunch is a system module (launch.xex) configured by launch.ini, which at boot loads up to five dynamic libraries into plugin slots (.xex files with the sysdll flag). Configuration entries:[S7]

launch.ini — excerptini
[Plugins]
plugin1 = Hdd:\xbdm\xbdm.xex          ; xbdm always first — other plugins may depend on it
plugin2 = Hdd:\plugins\LiveRedirect.xex ; our redirect plugin

A plugin is a native big-endian PowerPC library with the entry point DllMain(HINSTANCE, DWORD reason, void*), called on DLL_PROCESS_ATTACH (load) and DLL_PROCESS_DETACH (unload). Plugin code runs in system space beside xam.xex — it can read and write system memory and resolve module exports via GetModuleHandle/GetProcAddress.[S7]

7.2Function resolution and export-table patching

All xam.xex functions are addressed by ordinal number (full tables — Appendix A). The resolution pattern:[S7]

ResolveFunction — obtaining an export addressC++
void* ResolveFunction(const std::string& module, uint32_t ordinal) {
    HMODULE h = GetModuleHandle(module.c_str());
    return h ? GetProcAddress(h, reinterpret_cast<const char*>(ordinal)) : nullptr;
}

// exports needed for redirection (xam.xex):
DWORD  (*Real_XNetDnsLookup)(DWORD caller, const char* host, HANDLE ev, XNDNS** out) =
        (DWORD(*)(...))ResolveFunction("xam.xex", 67);   // NetDll_XNetDnsLookup
DWORD  (*Real_Connect)(DWORD caller, SOCKET s, const sockaddr* name, DWORD len) =
        (DWORD(*)(...))ResolveFunction("xam.xex", 12);   // NetDll_connect

The hook itself replaces the export-table entry with the address of our function (the same technique community plugins already use). Required behavior: (1) save the original pointer; (2) the new function has an identical signature (including the leading XNCALLER_TYPE); (3) restore the originals on DETACH. Because we patch the pointer, not function code, updates that relocate code do not break the hook (as long as the ordinal is unchanged — the AX tables show NetDll numbers are stable across dashboard versions, since titles link by them).

7.3LiveRedirect plugin skeleton (pseudocode, part 1)

LiveRedirect.xex — redirection core (part 1/2)C++ (pseudocode)
// ============ 1. Mapping table ============
struct RedirectRule { const char* hostSuffix; uint32_t targetIpBe; uint16_t targetPortBe; };
static const RedirectRule g_rules[] = {
    { "xboxlive.com", HTON32(COMMUNITY_IP), 0 },   // DNS: suffix match
    { "xbox.com",      HTON32(COMMUNITY_IP), 0 },
};
// Port mapping for TCP traffic (optional)
static uint32_t MapIp(uint32_t ipBe)  { return CommunityIpSet(ipBe) ? COMMUNITY_IP_BE : ipBe; }
static uint16_t MapPort(uint16_t pBe) { return (pBe == HTONS(3074)) ? pBe : pBe; }

// ============ 2. DNS hook ============
static DWORD Hook_XNetDnsLookup(DWORD caller, const char* host, HANDLE ev, XNDNS** out) {
    for (auto& r : g_rules)
        if (HostMatchesSuffix(host, r.hostSuffix)) {
            // fill XNDNS ourselves: status=0, cina=1, aina[0]=r.targetIpBe
            FillXndns(out, r.targetIpBe);
            if (ev) SetEvent(ev);              // immediate readiness (async contract)
            return 0;
        }
    return Real_XNetDnsLookup(caller, host, ev, out); // other names → real DNS
}
LiveRedirect.xex — redirection core (part 2/2)C++ (pseudocode)
// ============ 3. TCP hook (connect) ============
static DWORD Hook_Connect(DWORD caller, SOCKET s, const sockaddr* name, DWORD len) {
    sockaddr_in mapped = *(const sockaddr_in*)name;
    if (CommunityTarget(mapped.sin_addr.s_addr))
        mapped.sin_addr.s_addr = COMMUNITY_IP_BE;         // rewrite destination address
    return Real_Connect(caller, s, (const sockaddr*)&mapped, len);
}

// ============ 4. DllMain — installation ============
BOOL DllMain(HINSTANCE h, DWORD reason, void*) {
    if (reason == DLL_PROCESS_ATTACH) {
        if (!InstallExportHook("xam.xex", 67, Hook_XNetDnsLookup, &Real_XNetDnsLookup)) return FALSE;
        if (!InstallExportHook("xam.xex", 12, Hook_Connect,          &Real_Connect))          return FALSE;
        // likewise: sendto(24), WSASendTo(25), XHttpConnect(205) — as needed
        ShowNotification(L"LiveRedirect: active");   // XNotifyQueueUI @656
    }
    if (reason == DLL_PROCESS_DETACH) {
        RemoveExportHook("xam.xex", 67, Real_XNetDnsLookup);
        RemoveExportHook("xam.xex", 12, Real_Connect);
    }
    return TRUE;
}

7.4Safety and stability rules

  • Atomic patching — the export-table pointer swap must be a single aligned store; never leave a "half-hooked" state.
  • Idempotent DETACH — unload restores original pointers; if later plugins fail to load, the system is not left with a corrupted table.
  • Threads — hooks are called from many threads (title, dashboard, system threads); the mapping table is read-only after ATTACH; any state needs locks (or lock-free — contention is low).
  • XNCALLER_TYPE — the hook sees the caller context (C3.1); you can log or map SYSAPP vs TITLE traffic differently.
  • Base address — plugin baseaddr > 0x90000000, no collisions with other plugins (community example: 0x91D00000).[S7]
  • Configuration — read mapping rules from a file (e.g. Hdd:\plugins\LiveRedirect.ini) or a launch.ini section, so a server change never requires recompiling.

Chapter 8 · Server
Community server — reference architecture

This chapter defines what must exist on the other side for redirected traffic to end in a working online session. The model is dictated by console behavior (C4–C5): every "expected answer" of the console is a required server component. The architecture deliberately mirrors what Insignia achieved for Live 1.0 (a closed service rebuilt by closed-source reverse engineering and maintained for 216 games).[S12]

8.1Recommended implementation order

  1. DNS + HTTP CDN — cheapest start, pure HTTP, zero cryptography; instant visible effect in the dashboard (icons/box art — URL patterns from Table 4.1).
  2. QoS responder + UPnP — lets the network test complete; the console handles UPnP itself via NetDll_Upnp* (the server simply must not block it).
  3. Console registration + sign-in — the heart of the system; requires RE of the ticket format (gap from C5.2); the challenge/response exchange pattern is the XnpLogon* export family.
  4. Presence and matchmaking — the first visible win for players; exchanging XNADDR between consoles (as in System Link — XNKID as the session identifier).
  5. Storage/TU — raising service quality to a full Live analog.

8.2Game traffic: relay vs P2P

After matchmaking, a player console hosts or connects to peers over VDP sockets (UDP 3074) with XNKEY-encrypted traffic. Two server models: (a) P2P — the server only hands participants each other's XNADDR (the Live and Insignia model: gameplay is console↔console)[S10][S12]; (b) relay — relay servers tunnel the encrypted packets (the XLink Kai model — requires patching the 30 ms limit on the console or very low relay latency).[S12][S13] Recommendation: P2P by default + relay for "symmetric NAT" pairs where P2P cannot negotiate.

8.3Clock and the "2025 cap"

The server should: (a) return KDC time in the sign-in response and accept a wide console-RTC deviation window; (b) not enforce TLS certificate validity on system traffic (use HTTP, C6-L3a); (c) document tools like TimeFixer for consoles with an exhausted RTC.[S22]

Chapter 9 · Prior art
Prior art — what already works in the community

None of the projects described here is a mere curiosity — each solves a piece of the same puzzle. Below, a synthesis of their documentation and code.

9.1Insignia — the full resurrection of Xbox Live 1.0 (OG Xbox)

The closest template for a 360 project. A non-commercial, closed-source replacement for the original Xbox Live: closed beta 2022, open beta with 25 games in November 2022, Halo 2 servers in March 2024; it supports 216 of 381 Live games and over 36,000 users (2026).[S12] Rebuilt services: matchmaking, leaderboards, friends, invites, clans, UGC content, voice chat, updates/DLC for some titles.[S12] Onboarding: web account registration + console registration (on unmodified consoles via the one-shot "endgame" USB exploit); configuration: primary DNS 46.101.64.175; local insigniaDNS for restrictive ISPs.[S8][S9][S12] The protocol architecture was rebuilt from RE: Kerberos + Secure Gateway + UACS/Machine Accounts.[S10][S11] The directly transferable lesson: you do not need Microsoft's keys — it suffices that the server is the party issuing its own tickets, and the console accepts them because it trusts the server pointed to by DNS.

9.2XLink Kai — System Link tunneling (OG + 360)

Team XLink's long-running service: an engine on a PC/RPi "glues" consoles into a virtual LAN (tunneling System Link broadcasts), with per-game and per-region arenas, XTag profiles, free, 1300+ games.[S12][S13] The exposed kaiEngine API (REST-like: GetActiveGames/v3, GetGameList/v3; arena vectors, per-game ping limits) shows what a presence/matchmaking layer looks like without touching Live protocols.[S13] Engineering lesson: the 30 ms System Link limit on the 360 (C3.6) — XLink documents it as a deliberate anti-tunneling safeguard; an RGH console can patch it.[S12]

9.3Aurora LiNK — the online service for RGH (360)

The service built into the Aurora dashboard for modified consoles: online play via System Link tunneling plus a social layer (friends, presence, notifications). Requires RGH partly because of the 30 ms limit. UNVERIFIED in technical detail (the creators' sites — realmodscene/Phoenix — were unreachable from this research environment); indirectly confirmed: community discussions about having to disable LiNK for clean LAN System Link, and about the service allowing one console per IP when hosting.[S22] Lesson: for an RGH audience, System Link + presence is enough — full Live sign-in is not a precondition for online play.

Chapter 10 · Meta
Risks, RE gaps, ethics and law

10.1Technical risks

  • Console stability — every memory patch can end the session in a crash; minimize the patch surface (hook pointers, not code), test on devkits/RGH with xbdm.
  • Dashboard versions — NetDll/XAM ordinals are stable (titles link by them), but XHttp/sign-in code paths may differ between 16537 and 17559; the hook assumes nothing about code, so it survives — but L3-c validations need per-version offsets.
  • The 30 ms limit — with relays we must patch or provide geographically close servers.[S12]
  • Clock — RTC cap and drift; the server must tolerate and correct time (C8.3).[S22]
  • Scaling — VDP sessions are P2P, so server load grows with presence/matchmaking, not game traffic — good news for cheap infrastructure.

10.3Ethics and legal framing (the community's perspective)

The 36C3/DEF CON talk puts it best: supporting abandoned networked devices that the vendor no longer updates is a form of heritage preservation, and the homebrew community's doctrine consistently separates interoperability (your own console, your own servers, keeping purchased games functional) from license circumvention (unauthorized content acquisition).[S11] A redirect project should: run only on the owner's hardware or with consent, not distribute vendor keys or content, not enable play of titles the user does not own, and be released non-commercially — exactly the mode Insignia operates in.[S12] Legal aspects (copyright, DMCA/EUCD interoperability provisions) differ between jurisdictions — consult local counsel before public distribution; this document is a technical analysis, not legal advice.

The console's real-time clock; bounded range (the "2025 cap") and drift — relevant to tickets and TLS.
